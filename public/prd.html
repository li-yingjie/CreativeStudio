Product decision brief · phase 1

把创意生成，变成可交付系统。

AI 创意工坊面向运营活动、设计素材与互动体裁，把一次性的生成结果升级为可规划、可调用资产、可精确编辑、可验证和可复用的业务交付。

原 PRD revision 4017 Demo baseline 2026-08-18 产品经理完整版 原文只读

一句话判断

问题需求分散在页面、物料、玩法和多个生产工具中，生成后仍需人工拼装。
答案用 Chat 规划任务，用 Canvas 承载全部产物，用 Editor 对真实对象精确修改。
边界不承诺“全自动替代设计”；一期先打通活动与素材交付，游戏能力分阶段迁入。
管理层5 分钟判断价值 产品评审15 分钟核对模型 研发对齐对象与验收边界
01 · Why now

不是缺少生成能力，而是缺少稳定的创意交付链路。

外部产品已经验证 Canvas、Skills、Memory 的工作台方向。抖音的差异不在“也能生成”，而在多体裁规模、真实分发场景和业务资产沉淀。 PRD §1.1–1.2

机会不是单点工具

页面、直播间、资源位、IP、游戏素材共享同一套任务上下文和资产治理，单独做“图片生成器”无法覆盖真实交付。

护城河是业务资产

Brand Kit、IP Kit、玩法模板、知识、模型和工具必须能被 Agent 精确调用，并留下版本、来源和授权证据。

一期先证明闭环

以运营活动与设计素材为主线，优先证明“需求 → 规划 → 生成 → 编辑 → 校验 → 交付”可重复，而非追求体裁数量。

ROLE 01 · 业务运营

把活动意图变成完整交付

在同一项目里描述目标、确认玩法与方向、试玩最终动线，并拿到页面、资源位、配置和文档，而不是继续跨工具拼装。

ROLE 02 · 设计协作

守住品牌与像素边界

把 Brand Kit、IP Kit、模板和源文件转成可调用资产；锁定不可变元素，接管多图层结果并对关键视觉做精确调整。

ROLE 03 · 研发平台

消费稳定、可验证的规格

接收有 schema、版本和校验结果的 ActivitySpec / RuntimeSpec，避免从自然语言、截图或不可追踪的临时代码中反推业务意图。

ROLE 04 · 治理与供给

让能力和资产持续复用

维护技能、工具、模型、知识、授权和规则注册表，追踪谁在何时引用了哪个版本，并能阻断不合规发布。

05 · Generation & confirmation gates

生成不是一次回答，而是可回放、可暂停、可重编译的 CompileRun。

每次生成都要能回答：用了哪些来源、通过了哪些人工确认、写入了哪个版本、失败后从哪里恢复。 产品架构基线 / P0

HUMAN GATE 01

锁定资产与边界

确认模板、Brand Kit、Style Profile / IP Kit、授权版本与不可变保护区。未确认前不批量生产。

HUMAN GATE 02

确认活动结构

确认核心用户动线、页面拓扑、玩法槽位、奖励方案和交付矩阵，防止在错误结构上继续铺量。

HUMAN GATE 03

首方向再传播

先完成一张代表性页面或素材并验收方向，再把同一规则编译到其它尺寸、渠道与版本。

SINGLE EDITABLE FACTActivitySpec

活动意图与结构化配置的唯一事实源。页面结构、玩法实例、资产绑定和交付矩阵都通过版本化语义 Patch 更新。

DERIVED CONTRACTRuntimeSpec

由 Compiler 派生给 H5 / Lynx / Native 的运行合同。可预览、可验证，但不能成为另一份人工维护的配置真相。

EXTERNAL BUSINESS FACT业务运行状态

库存、资格、榜单、开奖、直播与用户完成态仍由业务系统拥有；工作台只配置绑定关系，不伪造“已接通”。

CompileRun 的可回放输入、阶段和证据

一次 CompileRun 从 SourceBundle 开始，按阶段产出候选结果、确认记录、语义 Patch、校验报告和最终版本。任何失败都应定位到最早偏离预期的阶段，而不是只在最终页面补丁式修复。

07 · Governance & product contracts

可交付系统的核心不是“能改”，而是知道谁能改、改了什么、为何可发布。

对象、资产、版本、权限、校验和运行事实必须能相互对账；否则 Demo 的灵活性会在生产环境变成不可控覆盖。 产品架构基线 / 编辑器规格

CONTRACT 01

Semantic Patch

Agent 和人工都通过可读的语义 Patch 修改 ActivitySpec；Patch 记录对象、字段、旧值、新值、原因和发起者。

  • 拒绝过期 revision
  • 支持 diff、撤销与重放
  • 禁止任意 React / 配置直写
CONTRACT 02

Operator ownership

人工确认或手工修改后，相关字段转为 operator-owned；Agent 后续编译默认保留，除非用户明确授权覆盖。

  • 锁定与保护区可见
  • AI 修改先给影响预览
  • 冲突进入人工确认
CONTRACT 03

Immutable version

每次保存形成草稿版本；已发布的 ActivityDeliverable 不可静默修改，只能基于旧版本派生新版本。

  • Actor 标记 agent / operator / import
  • 来源与资产版本固定
  • 支持比较和回滚
CONTRACT 04

Validation gates

schema、依赖、品牌、尺寸、授权、运行与发布规则分层执行；错误必须指向具体对象和修复动作。

  • 编辑时内联校验
  • 编译时全量校验
  • 发布时不可绕过门禁
生产性资产合同：不是“有张图”，而是六类信息完整

09 · Why interactive HTML

飞书原文负责持续共创，HTML 负责让决策发生。

两种载体互补：原稿继续作为业务需求、评论与修订源；本地已接受的架构 / 编辑器规格约束产品合同；HTML 将二者与 Demo 证据组织成评审、汇报和跨角色对齐层。

飞书 PRD 原稿

适合记录业务目标、多人评论和持续修改，保留所有背景材料和附件；产品合同缺失处不靠猜测补进原稿。

最佳场景撰写、评论、历史版本、逐条需求维护
信息形态长表格、嵌套列表、原始图片与关联文档
优势内容完整、协作成熟、编辑成本低

交互式决策 HTML

适合在有限时间里建立共同判断，并让不同角色进入各自需要的证据层。

最佳场景管理层汇报、产品评审、研发对齐、方案路演
信息形态指标图、产品闭环、可筛选矩阵、案例证据、对象合同
优势快速导航、可比较、可演示、可打印、可深链
10 · Roadmap, metrics & acceptance

路线图以可验证能力为单位，而不是以页面完成数量为单位。

日期沿用原 PRD；这里同时补充可衡量结果、关键风险与验收门，避免“Demo 看起来完整”替代生产就绪。 PRD 附录 / 专业补全建议

NORTH STAR首个可验证交付时间从 SourceBundle 完整到首方向通过 Gate 03；需按项目拓扑分层统计。
QUALITY一次验收通过率首次交付无需返工即通过尺寸、品牌、运行和发布门禁的比例。
REUSE受治理资产引用率正式交付中引用已注册 Brand / IP / Template / Style 版本的比例。
SAFETY人工接管与阻断准确率人工修改保留率，以及规则阻断中真实问题与误报的构成。

以上是基于当前产品机制提出的指标框架，不是已采集数据；正式立项前必须补 owner、分母、事件口径、时间窗、基线与目标值。

  • ActivitySpec 单写入点
  • RuntimeSpec 只派生
  • 变更全部走语义 Patch
RISK 02 · MOCK LEAKAGE

把演示交互误判为接通

Lynx Bridge、真实分层、生成、发布和授权仍有服务依赖。

  • 界面显式标注 mock
  • 验收区分 Demo / production
  • 未接服务不展示虚假成功

批量生成覆盖有效像素

Logo、Hot!、文字、安全区和人工调整可能被后续 Agent 静默破坏。

  • 最小可写区域
  • 保护区像素不变量
  • operator-owned 默认保留
