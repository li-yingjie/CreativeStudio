# 玩法拆解与配置说明

> 示例来源：[这夏夯爆了 · 暑期生活服务 UGC 活动方案](https://bytedance.larkoffice.com/docx/N3dmdaAj8o9tQoxt6CncSd1Xn7d)
> 老平台参考：[线上玩法内容与配置项](https://bytedance.larkoffice.com/docx/FrKsd229joEZBDxVnzTcAg0Cnlh)
> 本说明只解释玩法模型与配置口径，不修改原策划文档。

## 1. 一句话定义

“玩法”不是一张活动页，也不等于抽卡组件。它是一套可版本化的业务规则：在什么时间、让什么人、完成什么动作、获得什么机会、按什么概率和库存结算什么奖励，再由页面把这些规则呈现给用户。

本项目将玩法拆为五层：

| 层 | 解决的问题 | 主要对象 |
| --- | --- | --- |
| 活动层 Campaign | 为什么做、什么时候做、和谁合作 | 目标、周期、合作方、预算、活动状态 |
| 轨道层 Track | 用户在参与哪套独立记账与结算机制 | 阶段集装备主玩法、通用金豆副玩法 |
| 规则层 Rule | 什么动作能拿到什么，以及如何抽取和兑换 | 任务、机会、卡池、权重、保底、奖励、库存 |
| 体验层 Experience | 用户看到什么、不同状态如何反馈 | 页面结构、阶段主题、小马 IP、文案、动画、空态 |
| 运营层 Operations | 怎么安全上线、监控和回滚 | 环境、版本、灰度、门禁、监控、告警、审计 |

页面只是玩法运行时的一个消费者。任务事实、点亮结果、作者分层和金豆账户等数据应由对应业务系统提供，不能由前端配置伪造。

### 1.1 后台产品架构

活动玩法配置不是策划文档的阅读页，而是**玩法生成之后**出现的编辑器：

`解析方案 → 选择/生成核心玩法 → 生成可试玩版本 → 打开活动玩法配置 → 调参 → 保存/发布`

后台按两级组织：

| 级别 | 示例 | 职责 |
| --- | --- | --- |
| 一级：玩法类型 | 抽奖玩法、集卡玩法、任务玩法、投票玩法、答题玩法 | 决定使用哪种规则引擎，可组合启用 |
| 二级：参数面板 | 出奖手感、次数与保底、奖池权重、兑换档位、任务发放 | 直接编辑运行参数，并即时同步到试玩 |

策划文档只负责提供推荐类型、初始参数和业务约束，不决定后台页面的章节结构。同一种“抽奖玩法”应能被不同活动复用；不同活动只更换参与规则、玩法参数、奖品和素材。

当前 Demo 的组合是：

- 活动参与规则：管理生效时间、时区、每日重置时间、开放平台、活动入口、目标人群、地域、登录/实名要求、年龄、参与人认定和风险处理。
- 抽奖玩法：管理互动模板、入场资源、消耗、概率、权重、保底、中奖上限和账号/设备/IP 频控。
- 集卡玩法：管理卡名、卡面短文案、稀有度、掉落权重、素材绑定、赠送、按数量/全集/指定组合解锁和是否消耗卡片。
- 任务玩法：管理用户动作、完成依据、计数口径、周期、人群、有效期、频控、自动/手动领取、完成后去向和多状态文案；平台在后台把业务选项映射成事件。
- 奖品对象：独立管理类型、价值、日/总库存、人均上限、券模板/商品 SKU、发放方式、有效期、退款回收、邮寄信息和缺货兜底。
- 投票 / 答题玩法：候选项和题库是可导入的内容对象，分别与票数规则、答题节奏分离。

### 1.2 配置对象图

不把一个档位展开成几十个重复字段，而是在系统内部用稳定编号相互引用；运营界面只展示卡片名、奖品名和业务动作，不直接暴露这些编号：

```text
Gameplay Module
├── references → Content Pool / Task / Candidate / Question IDs
├── owns       → Probability, Frequency, Completion Rules
└── outputs    → Resource or prizeId

Prize
├── references → 券模板或商品 SKU
├── references → Asset Key
├── owns       → Inventory / Validity / Refund / Fallback
└── consumed by→ Collection Tier / Lottery Pool / Quiz Result

Content Object
├── owns       → Name / Description / Tags / Enabled State
└── references → Asset Key
```

这样更换券模板、卡图或任务文案时，不需要到所有档位里重复修改；发布校验也能发现无效引用。

### 1.3 对老平台的选择性吸收

| 结论 | 吸收方式 |
| --- | --- |
| 真实业务需求 | 任务计数维度/周期/有效期、奖品库存/履约/核销、卡池内容/概率/素材、反作弊、玩法联动、发布校验 |
| 运营效率需求 | CSV / JSON 按内容编号合并导入，素材按业务名称选择并直达素材库，修改立即同步试玩 |
| 需要重新抽象 | 旧平台的业务专属组件、SDK/FaaS 表单和巨大枚举不进入运营面板；平台在背后完成事件与履约适配 |
| 明确不继承 | 用页面组件名表示业务对象、同一奖品在多处重复录入、任务完成事实由前端按钮决定 |

当前页面明确不展示共享服务名、接口 ID 和“外部服务是否接通”检查。这些属于平台建设责任，不应转嫁给活动运营。运营侧只配置能作出业务决策的参数；字段和规则校验在保存/发布动作中按需反馈，不常驻成一张开发验收看板。

### 1.4 编辑器的信息呈现顺序

玩法配置采用“先理解、再修改”的渐进式结构，而不是把所有字段一次性铺开：

1. 首屏先展示当前活动实例、版本、运行状态和玩法关键数，让运营确认自己正在改什么。
2. 用完整规则链说明用户如何获得机会、如何参与、何时触发保底或结算，以及最终进入哪套奖励机制。
3. 紧接着列出本页可调整的业务维度；一级规则面板默认展开并可直接编辑，低频高级设置才默认收起。任何收起态摘要都必须完整呈现当前生效值。
4. 卡池、奖品、任务等集合对象先展示名称、状态和关键结果，同一时间只展开一个对象编辑，避免长表单失去上下文。
5. 库存覆盖、概率占比和机会总量等结果跟着字段就地更新；保存或发布时再做阻断校验，不另设常驻检查页。

玩法之间有关联，不代表后台需要共用一张总流程图。每个玩法页应围绕自己的运营决策组织：抽奖按抽取内容、出奖规则、参与规则、风险控制排列；集卡按卡册内容、兑换设置、赠送与反馈排列；任务、投票、答题同样采用各自的对象顺序。跨玩法关系只落在具体字段中，例如“抽奖机会来源”“卡册内容”“绑定奖品”，不再额外占用首屏解释整条逻辑。

## 2. 示例活动的玩法结构

### 2.1 阶段集装备主玩法

流程：完成阶段任务 → 获得抽装备机会 → 抽取或赠送装备 → 集齐指定数量 → 兑换优惠券或实物。

三个阶段共用同一套页面骨架、任务引擎与小马 IP，只替换主题参数：

| 阶段 | 场景 | 合作方 | 时间 | 变化项 |
| --- | --- | --- | --- | --- |
| 一起去玩水 | 玩水 | 品类营销｜玩水季 | 06/30–08/31 | 话题、POI、装备包装、阶段素材 |
| 一起去干饭 | 美食 | 到店餐饮｜夜食指南 | 07/20–08/31 | 话题、POI、装备包装、阶段素材 |
| 一起去遛娃 | 亲子 | 品牌传播｜海底小纵队 | 08/11–08/31 | 话题、POI、装备包装、阶段素材 |

阶段任务包括：

- 投稿：带话题定位或特效投稿，奖励 2 次抽装备机会；新作者额外 1 次，每日最多 3 次。
- 点亮：点亮指定商户，奖励 1 次抽装备机会，每日最多 10 次。
- 访问裂变：赠送装备给朋友，奖励 1 次抽装备机会，每日最多 3 次。

奖励门槛为集齐 2 / 4 / 6 / 9 种，对应四档券或实物奖励。

### 2.2 通用金豆副玩法

流程：完成通用任务 → 获得挖金豆机会 → 产出金豆 → 按 100 金豆 = 1 元折算 → 跳转抖音主站金豆页兑换。

它贯穿全部阶段，只换主题包装：玩水阶段“冲浪得金豆”、美食阶段“干饭得金豆”、亲子阶段“跑马得金豆”。

通用任务包括：

- 投稿：五类投稿动作，奖励 2 次挖金豆机会；新作者额外 1 次，每日最多 3 次。
- 点亮：点亮指定商户，奖励 1 次，每日最多 1 次。
- 访问与邀请：访问活动页奖励 1 次；邀请朋友奖励 2 次，每日邀请最多 3 次。
- 行为教育：访问分享计划、点击视频锚点、进入“去过”Tab、创建个人地图合集，奖励 1 次，每日最多 1 次。

两条轨道可以复用同一个“投稿完成”事实，但必须分别记账，避免一次回调重复发奖或不同奖励账户互相污染。

### 2.3 当前 Demo 的实际运行链路

当前线上终态是一套关联的组合玩法，而不是三个并列小游戏：

`首次赠送 12 次 + 任务每日最多再赚 14 次 → 每抽消耗 1 次、每日最多 20 抽 → 抽中 9 种夜食卡之一 → 集齐 2 / 4 / 7 种 → 领取 2 元券 / 5 元券 / 43 元券包`

抽卡概率分两层计算：先按当前用户持有状态，以 88% 倾向未拥有卡、12% 允许重复；再在“未拥有”或“已拥有”的对应分池内按卡片权重归一化。界面展示的单卡百分比是全部卡共同参与时的基础权重占比，不冒充所有用户状态下都恒定的最终概率。连续 6 抽后触发新卡保底。

小马黄金转运珠虽然仍在奖品库中，但没有绑定当前三个兑换档位，因此不会从主链路发放。配置台必须把这种“存在但未接入”的状态直接说清楚。

## 3. 创建过程

1. **冻结来源快照**：记录策划文档、修订号和解析时间，保证后续能追溯“配置从哪来”。
2. **结构化建模**：把自然语言拆成活动、轨道、阶段、任务、卡池、奖励和依赖，不直接把文档段落塞进页面。
3. **生成阶段实例**：从公共模板派生玩水、美食、亲子三个实例，只覆盖阶段差异。
4. **补齐可发布参数**：确认装备口径、奖品面额、日库存、总库存、时间和合作方白名单。
5. **确认参与与结算口径**：页面读取配置；运营只确认人群、任务完成条件、奖品模板和异常处理，平台负责把规则映射到真实能力。
6. **校验并发布**：Schema 校验、规则冲突校验、预算与库存校验通过后进入预览，验收后灰度发布。

## 4. 完整参数配置项

### 4.1 活动与阶段

- 活动 ID、名称、目标、活动状态、开始/结束时间、时区
- 阶段 ID、名称、场景、开始/结束时间、优先级、互斥/并行关系
- 合作方、话题白名单、POI 白名单、地域范围
- 阶段主题素材与公共模板版本

### 4.2 人群与准入

- 参与端、最低客户端版本、登录要求
- 新作者定义、存量/回流作者分层、任务排序策略
- 年龄、地域、黑白名单、风险账户排除
- AB 实验桶与灰度人群

### 4.3 任务与机会发放

- 任务 ID、轨道、类型、动作、完成条件、前置任务
- 事实来源、回调事件、去重键、结算周期
- 奖励资源类型、单次发放量、新人加成
- 每日上限、周期上限、全局预算、任务展示顺序
- 失败重试、补发策略、过期策略

### 4.4 抽取与卡池

- 初始机会、单次消耗、卡池版本
- 卡片/装备 ID、名称、稀有度、基础权重
- 未拥有卡倾斜、保底次数、权重动态调整规则
- 重复卡处理、赠送门槛、赠送次数、接收限制
- 抽取记录、幂等键、防刷频控

### 4.5 奖励与库存

- 集齐门槛、奖励类型、券面额或实物 SKU
- 每日库存、总库存、人均领取次数、奖品预算
- 发奖渠道、到账时限、兑换有效期、使用门槛
- 库存不足兜底、发奖失败补偿、退款/回收规则

### 4.6 金豆副玩法

- 机会来源、单次金豆产出区间、概率分布、保底
- 100 金豆 = 1 元的换算口径与活动期上限
- 金豆账户系统、兑换入口、跳转参数、回跳地址
- 与阶段主玩法共享的任务事实及独立记账键

### 4.7 内容与体验

- 小马 IP 强制露出位置、阶段主题包装、合作方标识
- 任务文案、进度文案、抽取结果、集齐反馈、兑换反馈
- 加载、空态、限频、库存不足、失败、重试文案
- 卡面、KV、动画、音效、适老化与无障碍配置
- 页面曝光、点击、任务、抽取、赠送、兑换等埋点

### 4.8 发布与风控

- 草稿/预览/线上环境、版本号、版本差异、审批人
- 生效时间、灰度比例、实验桶、发布门禁、回滚版本
- 机会发放、抽取分布、任务完成率、兑换成功率监控
- 日预算、总预算、日库存、总库存阈值与告警人
- 黑名单、设备/IP/账户频控、异常补发与操作审计

### 4.9 批量导入契约

当前 Demo 支持 CSV 和 JSON（数组或 `{ "items": [...] }`），单文件不超过 2 MB、最多 500 条。导入按 `id` 合并：同 ID 更新，新 ID 追加，未出现的旧数据保留，避免误覆盖在线内容。

| 对象 | 必填 | 主要可选字段 |
| --- | --- | --- |
| 卡池内容 | `id`, `name` | `motto`, `rarity`, `weight`, `assetKey`, `enabled` |
| 奖品 | `id`, `name` | `type`, `valueLabel`, `dailyStock`, `totalStock`, `perUserLimit`, `fulfillmentId`, `fulfillmentMode`, `validityDays`, `stockReset`, `refundPolicy`, `shippingRequired`, `assetKey`, `fallbackPrizeId`, `enabled` |
| 任务 | `id`, `label` | `subtitle`, `taskType`, `eventSource`, `eventKey`, `audience`, `countDimension`, `resetCycle`, `dailyLimit`, `reward`, `claimMode`, `cooldownSeconds`, `validFrom`, `validTo`, `jumpSchema`, `completedCopy`, `expiredCopy`, `assetKey`, `enabled` |
| 投票候选项 | `id`, `name` | `description`, `assetKey`, `enabled` |
| 题库 | `id`, `question`, `options` | `answer`, `difficulty`, `assetKey`, `enabled`；CSV 的 `options` 用 `|` 分隔 |

生产实现还应再增加三步：导入预览与差异确认、字段级错误报告、一键回滚到导入前版本。

## 5. 运行管理

建议采用“不可变版本 + 环境指针”：每次发布生成新版本，线上环境只切换当前版本指针。出现问题时回滚指针，不原位修改已生效记录。

运营后台至少要支持：

- 按活动、轨道、阶段查看当前生效版本和未来定时版本。
- 查看来源修订、配置差异、发布人、审批人和发布时间。
- 在发布动作中执行字段、时间、任务上限、奖励库存、预算和规则冲突校验，并把问题定位到具体配置项。
- 监控任务完成率、机会发放、抽取分布、集齐率、库存消耗、兑换成功率和裂变系数。
- 紧急暂停某个任务、某个奖励或某个阶段，并能回滚到上一稳定版本。

## 6. 当前 Demo 已暴露出的真实决策

当前活动期为 63 天，夜食阶段使用 9 张卡、3 个兑换档位和 3 个生效任务。配置台会直接呈现参数修改后的业务结果，而不是另做一张常驻“配置检查”看板：

1. **库存计划明显不足**：2 元券按日上限发放只覆盖 15 天，缺 357,981 份；5 元券覆盖 17 天，缺 91,449 份；43 元券包覆盖 25 天，缺 7,348 份。运营需要下调每日上限、补充总库存，或明确库存耗尽后的替代奖品。
2. **任务供给与消耗口径已可核算**：三项任务每天最多提供 14 次抽卡机会，抽卡玩法每日上限为 20 次；其中投稿任务单用户活动期理论上限为 630 次机会。是否保留这么高的累计供给，需要结合目标参与频次和预算再定。
3. **终极实物奖当前未进入兑换档位**：小马黄金转运珠仍在奖品库中，但现行三档只绑定 2 元券、5 元券和 43 元券包。它可作为后续档位或运营加奖，不应误认为当前主链路必发。
4. **平台侧责任仍需闭环**：投稿审核、赠卡领取、有效访问等完成事实需要平台建设方明确 owner、去重和失败补偿；运营只选择“什么算完成”，不填写服务名、接口 ID 或 SDK 参数。
