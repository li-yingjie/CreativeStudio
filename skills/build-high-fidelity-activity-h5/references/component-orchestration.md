# 玩法组件库调度协议

## 目标

组件库不是一套固定页面模板，也不是“发现卡片就套卡片”。它负责提供已经验证过的玩法能力、状态机和编辑契约。流程 Skill 根据玩法配置调度组件；Brand Kit 再通过视觉槽位给组件换肤。

## 调度输入

从已确认的玩法配置提取能力需求：

- 核心动作：寻找、投票、收集、合成、助力、签到、抽奖、投稿、预约等；
- 循环结构：单次、每日、累计、协作、章节式、阵营式；
- 状态：默认、进行中、已完成、已领取、已锁定、失败、空态；
- 数据形态：单对象、列表、排行、进度、关系网络、时间线；
- 反馈：即时动效、数值变化、奖励、解锁、分享回流；
- 编辑需求：哪些文本、图片、按钮、规则、奖励和重复项必须可单独选中。

## 调度顺序

1. 在组件注册表中按“能力契约”检索，而不是按组件外观名称检索。安装了 `$activity-h5-component-library` 时，先用其 `query-registry.mjs` 得到候选和覆盖率。
2. 依次核对平台适配、交互契约、数据形态、状态覆盖、可编辑槽位、无障碍和 Brand Kit 槽位兼容性。
3. 多个候选都满足时，优先选择状态更完整、已有活动验证更多、改动更少的组件。
4. 用玩法配置实例化组件；业务文案、奖励数值、素材和视觉皮肤不得写死在组件内。
5. 找不到完整组件时，组合注册表中的基础能力组件；仍不满足时才创建项目局部组件。
6. 新组件先作为项目候选，不自动污染通用组件库。经过复用和契约稳定后再提炼入库。

当前本地生产合同注册表为 `knowledge.activity-h5-components@1.0.0`，包含 Campaign Hero、篇章旅程、二元投票、内容榜单/发现、心愿墙、任务-机会账本、抽奖机和分会场积分八类组件。它提供合同而非框架实现；目标端仍需实现并通过对应 QA 场景。

## Figma 输入下的组件映射

- 读取 Figma 的组件、实例、variant、属性和交互原型；有 Code Connect 或现有代码映射时优先使用。
- 先把 Figma 节点映射为页面语义和行为契约，再匹配注册表组件。视觉上的 Group 不一定是代码组件，外观相似也不代表状态机相同。
- Figma 已定义的组件边界可以作为重要证据，但不能覆盖运行时交互、数据和可编辑性要求。
- 如果注册表组件的结构与 Figma 目标兼容，复用行为并用 Brand Kit/素材槽位还原视觉。
- 如果强行套用现有组件会破坏几何、状态或还原度，创建项目局部组件并记录 `source: project`，不要伪装成已复用。
- 对每个关键 Figma 节点保留 `figmaNodeId` 或等价来源定位，便于区域级截图对比和回放。

## 必须保留的组件记录

每个最终组件节点至少记录：

- `ref`：编辑器稳定选择标识；
- `kind`：语义类型；
- `source`：`registry`、`composed` 或 `project`；
- `registryId` 和 `version`：来源为注册表时必填；
- `config`：玩法配置，不含不可追踪的隐式常量；
- `states`：实现和验收过的状态；
- `slots`：文本、图片、按钮、奖励、装饰等可编辑槽位；
- `brandBinding`：槽位如何映射到 Brand Kit token 和素材；
- `dataBinding`：本地 mock 或真实接口的数据契约。

## 组件和 Brand Kit 的边界

- 组件拥有行为、状态、数据契约、可编辑结构和基本可访问性。
- Brand Kit 拥有色彩角色、字体层级、形状、材质、深度、图标、动效语言和生图提示词。
- 素材库拥有具体活动的 KV、艺术字、角色、奖励、场景和装饰文件。
- 页面蓝图决定组件的顺序、层级、节奏和跨组件状态联动。

一个投票组件可以在七夕活动中表现为“找喜鹊”，在 ACG 活动中表现为“夯/拉”，但其选择、计数、反馈和结果状态契约可以复用。

## 禁止项

- 不得因为视觉相似就复用交互契约不一致的组件。
- 不得把活动专属角色、标题、配色或奖励写进通用组件。
- 不得让 Brand Kit 改写组件状态机。
- 不得把整个页面注册成一个不可拆分的“万能 H5 组件”。
- 不得为了复用而牺牲主要玩法完整度；项目局部组件是允许的，但必须记录来源。
